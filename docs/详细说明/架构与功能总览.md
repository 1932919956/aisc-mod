## 三、三层架构

### 3.1 目标架构（定稿）

```
┌──────────────────────────────────────────────────────────────┐
│ 第 1 层  Agnes 战略层（外部大模型 agnes-2.5-flash）            │
│   回答"现在该干什么"：今天的目标、优先级、要不要去挖矿/建房     │
│   拿到的是压缩过的真实状态，输出的是意图，不是方块坐标          │
└───────────────────────────┬──────────────────────────────────┘
                            │  一次战略询问
┌───────────────────────────▼──────────────────────────────────┐
│ 第 2 层  车万女仆原生 Agent（执行层，TLM 1.5.2+ 自带）         │
│   模型 → 工具调用 → 游戏执行 → 结果回给模型，循环              │
│   对话历史、气泡显示、工具 schema 全由 TLM 负责                │
│   我们只做两件事：① 注册工具 ② 把一句战略意图变成一句消息       │
└───────────────────────────┬──────────────────────────────────┘
                            │  工具调用
┌───────────────────────────▼──────────────────────────────────┐
│ 第 3 层  女仆实体原生 Task / 动作机                            │
│   走路、寻路、破坏方块、攻击、合成、放方块                      │
└──────────────────────────────────────────────────────────────┘
```

**为什么这么分**：早期版本自己写了一套"模型→动作"的执行器，结果绝大多数 bug 都出在这一层（动作白名单不同步、状态机卡死、说要做却没做）。TLM 1.5.3 本身已经实现了完整的 function-call 循环，重复造它才是问题根源。

**接口**：`@LittleMaidExtension` + `ILittleMaid.registerAITool(ToolRegister)`（软依赖，只在装了车万女仆时加载）。工具实现 `ITool<T>`：`id / summary / parameters / codec / onCall / invocationSummary`。

### 3.2 现状对照（诚实版）

| 层 | 状态 | 说明 |
| --- | --- | --- |
| 第 1 层 Agnes 战略层 | ✅ 已在跑 | 自己的 HTTP 通道调用 `apihub.agnes-ai.com/v1/chat/completions`，模型 `agnes-2.5-flash` |
| 第 2 层 原生 Agent 工具 | 🔧 刚开始接 | 1.0.22 注册了第 1 个工具 `maid_situation`（只读）。真机验证：`VERIFY PASS agent-tools` |
| 第 3 层 执行 | ⚠️ 双轨 | 已在用：女仆原生 Task（`switch_work_task` 切任务）＋我们自己写的动作机（采集/挖竖井/打猎/建房/烧炼/存取）。动作机会逐步改写成原生工具 |

**一个 API Key 够不够**：够。TLM 的站点类是 `LLMOpenAISite`，有 `setUrl(String)` / `setSecretKey(String)` / `addModel(String)`（已在 1.5.3 的 jar 里确认存在），把它的 URL 指到 Agnes 的端点、用同一个 key 就行，不需要第二个 key。
**注意**：这一步（把原生 Agent 的站点指向 Agnes 端点）**还没有接线**。目前只有第 1 层那条 HTTP 通道在用这个 key。

## 四、一次完整的决策→执行流程

1. **每秒**（`maid.tickCount % 20 == 0`，且主人在线）：`MaidBridge` 的心跳 tick 跑一遍所有动作机（采集、挖掘、打猎、烧炼、建房、去地标），并更新她的"心境"数据。
2. **触发规划**（仅当真的闲着）：距上次规划满 `planningIntervalSeconds`（默认 30 秒），且没有正在进行的动作 → 组装状态快照。
3. **状态快照**给 Agnes：工作模式、跟随/坐下、作息、血量、背包食物、手持物、附近实体、装备、效果、位置、维度、可改世界与否、记忆里的地标、整合包知识、可选截图（`visionEnabled`）。
4. **Agnes 回一个"计划"**：`say`（她要说的话）＋ `think`（她的想法，走思考气泡）＋ `actions`（动作数组，每步含动作名与参数）＋ 可有可无的 `memory`。
5. **执行**：`MaidPlan.start()` 逐步跑，每一步落到具体动作机；**只有真实方块消失、真实物品入包才算成功**（`MaidBridge.blockedProgress()` 会识别"看起来成功其实没做"的措辞）。失败会把具体原因回传给 Agnes 并记进 `BlockedFieldTargets`，避免原地转圈。
6. **反馈**：结果写进 `mind` 的 `Outcome`，用气泡说出去；下一轮规划把上一次的真实结果带上去。
7. **同一秒内**：`MaidVoice.tick()` 负责"她主动开口"——安全、你在旁边、不在战斗中、冷却到了，才会说话（`MaidPersonality.mayChat`）。话从本地语料按心情/好感/时段/事件挑，不额外花 token。她只有在你**在线**时才会动手（`player == null` 直接返回），这是刻意的：你不在，她不做任何世界改动。

### 测试台翻过的两次车（这也是为什么上面的 PASS 可信）

1. **冻结的时钟**。第一版在 `ServerStartedEvent` 里死循环调用"每秒一次"的动作机。那时服务器还没
   开始 tick，**游戏时钟是冻结的**（同一次的状态报告里 `day_time=0` 就是铁证）；采集为了防重复
   调用有一道"距上次 tick 不足 20 游戏刻就返回"的闸门，时钟不走 → 第二次调用永远被挡 → 进度永远
   停在"1/2 秒"，石头永远不会掉。现在整套改成**跟着真实服务器 tick 跑**（每 20 tick 调一次，和真实
   心跳完全一致），顺带把真实寻路也测了。
2. **假通过**。挖竖井的场地先选在地表：一挖就通到水，mod 的安全规则立刻停下——这是**正确**行为，
   错的是测试场地。于是改成地表以下 20 格，结果更糟：这个世界地表在 y=-60、世界最低点是 y=-64，
   石头根本没放下去，一百格"虚空"被记成了"成功挖出阶梯"。现在改成空中封闭石室，**并且开测前先数
   一遍脚下实心方块**（少于 50/100 直接判失败），绝不再拿虚空当成绩。

### 这一轮抓出并修掉的真 bug：阶梯竖井卡在第 0 格（`MaidDig`）

判断"她有没有站上新台阶"时，代码比较的是她**面前**那个方块的位置。可那个方块刚被她自己挖空，它脚下
的地面也在同一轮被挖掉——那是个悬空的位置，谁也站不上去，等式永远不成立；十秒后她就报"挖到 0 格就
上不去了，停在这里"，竖井永远只有一格。
她真正落下去站住的位置是面前那一格的**下面**。比较对象和寻路目标都改成那一格后，竖井第一次真的
一层层往下走（`executor-dig` 从"40 秒无进展"变成"3 秒挖出阶梯"）。

这个问题只有在真实 tick 下才会暴露，也正好说明"先把执行器打牢、用真机验证"这条路是对的。
